# 웹소켓은 어떤 경우에 사용하며, HTTP 폴링 방식과 비교했을 때의 장단점은 무엇인가요?


> 과거에는 HTTP 폴링이나 롱 폴링을 통해 실시간을 흉내 냈지만 반복 요청/응답 구조로 인해 비효율과 서버 부하가 발생했습니다.  
> 이러한 비효율을 해결하기 위해 HTML5에서 등장한 웹소켓은 한 번의 연결로 클라이언트와 서버가 지속적이고 양방향으로 데이터를 주고받을 수 있어 낮은 지연과 높은 효율성을 제공합니다. 웹소켓과 함께 알아 두어야 할 데이터 스트리밍 기술로 SSE도 있습니다. 따라서 ‘서버 → 클라이언트’ 단방향 스트리밍에는 SSE가 적합하고, 채팅/게임/협업 도구처럼 양방향 실시간 상호작용에는 웹소켓이 필요합니다.

- 보통의 웹의 상호 동작
	- 클라이언트가 요청 - 서버가 응답 하는 정해진 방식
- 하지만 현대 웹은 더 이상 정보만 보여주는 역할만 하지 않음

### 기존 방식의 한계: HTTP 폴링

1. **HTTP 폴링이란?**
	1. 과거에 실시간 통신을 흉내 낸 방법
	2. HTTP는 기본적으로 클라이언트가 요청을 보내야만 서버가 응답할 수 있는 단방향 구조이다. 서버에 새로운 데이터가 생겼다고 해서 서버가 먼저 클라이언트에 말을 걸 수는 없다.
		1. 위 구조를 극복하기 위해 폴링 기법을 사용
2. **종류**
	1. **일반 폴링**
		1. 클라이언트가 일정 주기마다 서버에 반복적으로 요청을 보내는 방식
		2. 대부분의 경우 서버의 응답은 ‘아직 변경 사항 없음’일 가능성이 큼
		3. 실제로 전달할 새로운 데이터가 없음에도 불필요한 요청과 응답이 반복되면서 네트워크 자원이 낭비되고 서버에도 부하가 쌓임
	2. **롱 폴링**
		1. 클라이언트가 한 번 요청을 보내면 서버는 즉시 응답하지 않고 새로운 데이터가 생길 때까지 연결을 유지
		2. 데이터가 준비되는 순간 응답을 보내고 클라이언트는 다시 새로운 요청을 보냄
		3. 불필요한 응답은 줄어들지만 여전히 요청과 응답이라는 HTTP의 기본 구조를 벗어나지 못함
		4. 연결을 오래 유지해야 하므로 서버 자원에 부담이 될 수 있음
		5. 결국 하나의 요청은 하나의 응답으로 끝난다는 한계

### 웹소켓의 등장

1. **웹소켓이란?**
	1. HTTP 폴링과 같은 비효율을 해결하기위해 HTML5에 표준으로 등장
	2. 클라이언트와 서버 간에 하나의 TCP 연결을 계속 유지하며 양방향으로 자유롭게 데이터를 주고받을 수 있는 통신 프로토콜
2. **간단 개요**
	1. 먼저 클라이언트의 요청으로 통신이 시작되고 서버와의 핸드셰이크 과정을 거쳐 기존 HTTP 프로토콜에서 웹소켓 프로토콜로 진화
	2. 일단 연결이 맺어지면 매번 새로 요청할 필요 없이 서버와 클라이언트가 하나의 통로를 통해 실시간으로 양방향 데이터를 주고받을 수 있게 됨
3. 웹소켓은 지속적인 연결을 통해 낮은 지연 시간과 높은 효율성을 제공하며 진정한 의미의 실시간 양방향 통신을 할 수 있게 한다.
4. **웹소켓을 사용하는 상황**
	1. **실시간 채팅 앱**
		1. 카카오톡, 디스코드와 같이 보내는 것과 받는 것이 모두 즉시에 일어나는 서비스
	2. **온라인 멀티플레이어 게임**
		1. 나의 움직임, 다른 플레이어의 움직임이 실시간으로 전달되는 서비스
	3. **실시간 주식/코인 시세 알림**
		1. 서버에서 변동된 가격 정보가 수많은 클라이언트에게 동시에, 즉시 전달되는 서비스
	4. **실시간 위치 공유 서비스**
		1. 배달 라이더 추적처럼 지속적으로 실시간 위치를 파악할 수 있는 서비스
	5. **협업 편집 도구**
		1. 구글 독스, 피그마처럼 여러 사용자의 커서 위치나 입력 내용이 실시간으로 모든 참여자에게 공유되는 서비스

### 웹소켓과 SSE

1. **SSE란? (Server-Sent Events)**
	1. 서버에서 클라이언트로 이벤트를 전송하는 단방향 스트리밍 기술
		1. 실시간 알림이나 뉴스 피드처럼 서버의 데이터를 받아 표시하기만 하면 되는 서비스에 적합
2. **웹소켓과 SSE 비교**

	| 구분       | 웹소켓                                                 | SSE                                                             |
	| -------- | --------------------------------------------------- | --------------------------------------------------------------- |
	| 통신 방향    | 양방향                                                 | 단방향                                                             |
	| 연결 프로토콜  | ws:// 또는 wss:// 전용 프로토콜 사용                          | 일반 HTTP 프로토콜 기반                                                 |
	| 장점       | 진정한 양방향 통신 가능,
	높은 성능                                | HTTP 기반이라 구현이 비교적 간단, 
	자동 재연결 기능 내장                             |
	| 단점       | 별도 프로토콜이라 서버 설정이 필요할 수 있음                           | 단방향 통신만 가능                                                      |
	| 주요 사용 사례 | 실시간 채팅, 온라인 게임, 협업 툴 등 클라이언트의 입력이 서버에 즉시 반영 되어야 할 때 | 실시간 뉴스 피드, 주식 시세 업데이트, 스포츠 경기 스코어 알림 등 클라이언트가 데이터를 수신하기만 하면 될 때 |
