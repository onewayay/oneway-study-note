# 상태관리 라이브러리 비교

<details>
<summary>Zustand</summary>
1. 특징
	1. **최소한의 API**로 간단하고 직관적인 상태 관리를 제공합니다. Provider 없이 사용 가능하며, hook 기반으로 자연스럽게 React와 통합됩니다.
	2. `create()` 하나로 store + action 동시 정의
	3. **Store**

		```typescript
		import { create } from "zustand";
		
		interface CounterState {
		  count: number;
		  countDown: (step: number) => void;
		  countUp: (step: number) => void;
		}
		
		const useCounterStore = create((set, get) => ({
		  count: 10,
		  countDown: (step) => set({ count: get().count - step }),
		  countUp: (step) => set((state) => ({ count: state.count + step })),
		}));
		
		export default useCounterStore;
		```

		1. 상태와 상태를 관리하는 함수로 구성되며 커스텀 훅으로 작성
		2. `create` 함수로 생성하고 create 함수에 인자로 전달하는 함수에서 상태 정의와 상태관리 로직을 구현한 함수를 객체로 반환
		3. create에 인자로 전달하는 함수의 매개변수
			1. set
				1. set(newState): 상태를 newState로 업데이트
				2. set(state => newState): 이전 상태를 인자로 받고 newState를 반환하면 반환된 상태로 업데이트 됨
			2. get: 이전 상태를 반환하는 함수
2. 장점
	1. **보일러플레이트 거의 없음** — 몇 줄로 store 생성
	2. Provider 불필요 (앱 래핑 없음)
	3. 번들 사이즈 매우 작음 (~1KB)
	4. React 외부에서도 상태 접근 가능
	5. 필요한 부분만 구독 → 불필요한 리렌더링 방지
3. 단점
	1. 대규모 앱에서 구조가 흐트러지기 쉬움
	2. Redux DevTools보다 디버깅 도구가 상대적으로 약함
	3. 상태 구조화에 대한 컨벤션이 없어 팀마다 다를 수 있음

<summary>combine</summary>
- 결합하다라는 뜻
- creat로 새로운 store를 생성할 때 상태와 액션함수들을 한번에 객체에 넣지 않고
<u>상태는 상태끼리 액션함수는 액션함수끼리 서로 분리해서 작성하고 결합하는 방식</u>
- 추가로 타입을 더 정확히 추론하도록 도와준다.
- combine의 두개의 인수
	- 첫번째 : 객체 형태로 <u>store에 포함될 state를 명시</u>
	- 두번째 : 콜백함수로 매개변수 set과 get을 받아 <u>액션함수들을 포함한 객체들을 리턴</u>
	- store 내부에 이 두개의 인수값들을 하나로 더한 것이 생성된다고 생각하면 됨

	```typescript
	// src > store > count.ts
	
	import { create } from "zustand";
	import { combine } from "zustand/middleware";
	
	/* combine */
	export const useCountStore = create(
	  combine({ count: 0 }, (set, get) => ({
	    actions: {
	      increase: () => {
	        set((store) => ({
	          count: store.count + 1,
	        }));
	      },
	      decrease: () => {
	        set((store) => ({
	          count: store.count - 1,
	        }));
	      },
	    },
	  })),
	);
	
	export const useCount = () => {
	  const count = useCountStore((store) => store.count);
	  return count;
	};
	
	export const useIncreaseCount = () => {
	  const increase = useCountStore((store) => store.actions.increase);
	  return increase;
	};
	
	export const useDecreaseCount = () => {
	  const decrease = useCountStore((store) => store.actions.decrease);
	  return decrease;
	};
	
	```

<summary>immer</summary>
- 액션함수에 상태 업데이트를 더 편리하고 간단한 코드로 진행하도록 불변성 관리를 도와줌
- <u>불변성 관리란?</u>
	- 원본 상태를 직접 접근해서 값을 변경하지 않고 변경될 값을 포함한 새로운 객체를 만들어서 전달하는 방식으로 업데이트 하는 것
	- 업데이트 해야하는 데이터가 복잡해질 수록 코드도 복잡해지기에 immer를 사용해서 간단하게 만들면 도움이 된다.
- immer 설치
	- `npm i immer`
- create 함수 내부에서 호출해서 combine 함수 전체를 감싸도록 작성하면 된다.
(combine이 없다면 create)
- 이제 객체의 속성에 직접 접근해서 값을 바꿀 수 있다.

```typescript
// src > store > count.ts

import { create } from "zustand";
import { combine } from "zustand/middleware";
import { immer } from "zustand/middleware/immer";

export const useCountStore = create(
  immer(
    combine({ count: 0 }, (set, get) => ({
      actions: {
        increase: () => {
          set((state) => {
            state.count += 1;
          });
        },
        decrease: () => {
          set((state) => {
            state.count -= 1;
          });
        },
      },
    })),
  ),
);

export const useCount = () => {
  const count = useCountStore((store) => store.count);
  return count;
};

export const useIncreaseCount = () => {
  const increase = useCountStore((store) => store.actions.increase);
  return increase;
};

export const useDecreaseCount = () => {
  const decrease = useCountStore((store) => store.actions.decrease);
  return decrease;
};
```

<summary>subscribeWithSelector</summary>
- 셀렉터 함수와 구독한다.
- <u>셀렉터 함수를 통해서 스토어의 특정 값을 구독함으로써 해당 값이 변경될 때마다 어떠한 기능을 추가로 수행하도록 설정</u>
(useEffect와 비슷)
- create 함수 내부에서 호출해서 immer 함수 전체를 감싸도록 작성하면 된다.
(immer가 없다면 combine, combine이 없다면 create)
- 이후에 subscribeWithSelector를 적용한 store에 subscribe이라는 메서드를 호출해주면 된다.(여기서는 useCountStore.subscribe())
- subscribe의 인수
	- 첫번째 : store에 어떠한 값을 구독할 건지 결정하는 셀렉터 함수
	- 두번째 : 첫번째 인수로 설정한 셀럭터 함수에서 설정한 값이 변경될 때마다 실행할 내용의 콜백함수.
		- 이  콜백함수를 리스터라고 한다.
		- 리스너 함수의 첫번째 매개변수 :  셀렉터 함수에서 설정한 값이 들어온다.
		- 리스너 함수의 두번째 매개변수 :  셀렉터 함수에서 설정한 값(리스너 함수의 첫번째 매개변수)이 업데이트 되기 이전의 값을 받을 수 있다.
		- 리스너 함수 내부에서 현재 스토어를 불러오거나 현재 스토어의 특정 값을 업데이트 하는 것도 가능
			- 현재값 불러오기 : `getState()` 메서드 사용
			- 업데이트 하기: `setState()` 메서드 사용. 값을 잘못 변경하면 무한루프 발생하니 주의

```typescript
// src > store > count.ts

import { create } from "zustand";
import { combine, subscribeWithSelector } from "zustand/middleware";
import { immer } from "zustand/middleware/immer";

export const useCountStore = create(
  subscribeWithSelector(
    immer(
      combine({ count: 0 }, (set, get) => ({
        actions: {
          increase: () => {
            set((state) => {
              state.count += 1;
            });
          },
          decrease: () => {
            set((state) => {
              state.count -= 1;
            });
          },
        },
      })),
    ),
  ),
);

useCountStore.subscribe(
  (store) => store.count,
  (count, prevCount) => {
    // Listener
    console.log(count, prevCount);

    const store = useCountStore.getState();
    // useCountStore.setState((store) => ({ count: 10 }));
  },
);

export const useCount = () => {
  const count = useCountStore((store) => store.count);
  return count;
};

export const useIncreaseCount = () => {
  const increase = useCountStore((store) => store.actions.increase);
  return increase;
};

export const useDecreaseCount = () => {
  const decrease = useCountStore((store) => store.actions.decrease);
  return decrease;
};
```

<summary>persist</summary>
- Store를 로컬, 세션 스토리지 등에 보관
- create 함수 내부에서 호출해서 subscribeWithSelector 함수 전체를 감싸도록 작성하면 된다.
(subscribeWithSelector가 없다면 immer, immer가 없다면 combine, combine이 없다면 create)
- persist로 감싸고 객체형태의 옵션을 두번째 인수를 전달해야 한다.
- 옵션으로 넣을 프로퍼티
	- name : store가 브라우저의 스토리지에 저장될 때 사용될 이름
	- partialize : 스토어의 값들 중에 어떤 것들을 스토리지에 보관할지 명시
	- storage : 어느 스토리지에 넣을지. 기본은 로컬스토리지.
- 액션 객체 안에는 액션함수들이 들어가 있지 않는다
→ 스토리지에 JSON 형태로 전달해야하는데 함수는 JSON형태 변환이 불가능해서..
	- 해결
		- 옵션 객체 안에 partialize 함수를 넣어서 전달
		- 액션함수 말고 상태만 전달한다.
		- 이렇게 안하면 액션함수가 먹통된다.
- 로컬 스토리지가 아닌 세션 스토리지에 store 저장하기
	- reateJSONStorage 임포트 후, 옵션 객체에 storage 옵션과 함께 설정

```typescript
// src > store > count.ts

import { create } from "zustand";
import {
  combine,
  subscribeWithSelector,
  persist,
  createJSONStorage,
} from "zustand/middleware";
import { immer } from "zustand/middleware/immer";

export const useCountStore = create(
  persist(
    subscribeWithSelector(
      immer(
        combine({ count: 0 }, (set, get) => ({
          actions: {
            increase: () => {
              set((state) => {
                state.count += 1;
              });
            },
            decrease: () => {
              set((state) => {
                state.count -= 1;
              });
            },
          },
        })),
      ),
    ),
    {
      name: "CountStore",
      partialize: (store) => ({
        count: store.count,
      }),
      storage: createJSONStorage(() => sessionStorage),
    },
  ),
);

useCountStore.subscribe(
  (store) => store.count,
  (count, prevCount) => {
    // Listener
    console.log(count, prevCount);

    const store = useCountStore.getState();
    // useCountStore.setState((store) => ({ count: 10 }));
  },
);

export const useCount = () => {
  const count = useCountStore((store) => store.count);
  return count;
};

export const useIncreaseCount = () => {
  const increase = useCountStore((store) => store.actions.increase);
  return increase;
};

export const useDecreaseCount = () => {
  const decrease = useCountStore((store) => store.actions.decrease);
  return decrease;
};
```

<summary>Zotai</summary>
1. 특징
	1. **원자(Atom)** 단위로 상태를 분리 관리하는 bottom-up 방식
	2. React의 `useState`와 가장 유사한 API를 가지며, Recoil에서 영감을 받아 아이디어를 계승하여 만들어짐
	3. 가볍고 단순한 구조를 가지며, key가 필요 없고 Provider도 선택적으로만 사용
	4. Atom → 파생 Atom(selector) → Component 구독
2. Atom
	1. atom은 상태를 정의하는데 사용
	2. Jotai는 여러 종류의 상태를 관리할 수 있는데 atom은 상태의 일부를 나타냄(로그인 상태, 다크모드 여부 상태 등 상태값 하나)
	3. atom의 값을 읽는 컴포넌트들은 암묵적으로 atom을 구독하게 됨
	4. atom이 바뀌면(상태가 바뀌면) 그 atom을 구독하는 모든 컴포넌트가 리렌더링 됨
3. 장점
	1. **React 친화적** — `useState`와 거의 동일한 사용감
	2. 원자 단위 구독 → 정밀한 리렌더링 제어
	3. TypeScript 지원이 매우 자연스러움
	4. Suspense / React 18 동시성 모드와 궁합이 좋음
	5. 파생 상태(derived atom) 표현이 직관적
	6. 서버사이드 렌더링(SSR) 지원
	7. 작은 번들 크기, 빠른 업데이트
4. 단점
	1. Atom이 많아지면 관리가 복잡해질 수 있음
	2. Redux보다 미들웨어 생태계가 작음
	3. 전역 구독 패턴이 없어 큰 state 흐름 추적이 어려울 수 있음

<summary>Redux</summary>
1. 특징
	1. Redux는 **Flux 아키텍처**를 기반으로 한 예측 가능한 상태 컨테이너.
	2. 단방향 데이터 흐름과 엄격한 구조가 핵심
		1. Store → Action → Reducer → State
		2. 컴포넌트(이벤트 발생) → 액션(작업 정의) → 리듀서(상태 관리) → 스토어(상태 저장) 순으로 한 방향으로 흐름
	3. Redux 흐름
		1. **Store**
			1. 애플리케이션 전체 상태를 한 곳에서 관리하는 중앙 저장소
			2. Store를 보면 현재 상태와 상태 변경 기록을 알 수 있음
			3. Flux와 달리 상태 변경 작업은 Reducer라는 별도 함수로 나눠서 관리해 복잡성을 줄임
		2. **ActionCreators**
			1. 상태를 변경하기 위해 액션을 만드는 역할
			2. 액션을 Store로 전달(dispatch)하면 Store는 이걸 Reducer에 넘김
			3. Reducer가 새로운 상태를 만들어 반환하면, 이 상태가 Store에 저장됨
		3. **Reducers**
			1. 상태 변경 로직을 처리하는 순수 함수
			2. 기존 상태를 복제한 뒤, Action의 요청에 따라 새로운 상태를 생성해 반환
			3. 상태가 변경될 때마다 새로운 상태 객체가 생성되므로, 변경 내역 추적이 쉬워짐

```typescript
// store/counterSlice.js

import { createSlice } from '@reduxjs/toolkit';

const counterSlice = createSlice({
  name: 'counter',
  initialState: { value: 0 },
  reducers: {
    increment: (state) => { state.value += 1; },
    decrement: (state) => { state.value -= 1; },
  },
});

export const { increment, decrement } = counterSlice.actions;
export default counterSlice.reducer;
```


```typescript
// store/index.js

import { configureStore } from '@reduxjs/toolkit';
import counterReducer from './counterSlice';

export const store = configureStore({
  reducer: { counter: counterReducer },
});
```


```typescript
// Component.jsx

import { useSelector, useDispatch } from 'react-redux';
import { increment } from './store/counterSlice';

function Counter() {
  const count = useSelector((state) => state.counter.value);
  const dispatch = useDispatch();
  return <button onClick={() => dispatch(increment())}>{count}</button>;
}
```

### 선택 가이드

- **Redux** → 대규모 팀, 엄격한 구조와 디버깅이 최우선, 이미 Redux 기반 프로젝트
- **Zustand** → 빠르게 개발해야 할 때, 심플하고 유연한 구조 원할 때, Provider 없이 쓰고 싶을 때
- **Jotai** → React 철학에 가장 가까운 방식, 세밀한 상태 분리가 필요할 때, Suspense와 함께 쓸 때

>  **요즘 트렌드:** 신규 프로젝트에서는 Zustand나 Jotai를 먼저 고려하고, 서버 상태는**TanStack Query**와 함께 조합하는 방식이 인기입니다.
