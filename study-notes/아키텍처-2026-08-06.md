# 아키텍처

1. **"어떻게 구성할 것인가"에 대한 설계**
	1. 유지보수성, 확장성, 성능을 극대화하기 위한 구조적 설계 (코드 구성, 파일 구조, 데이터 흐름)
2. 아키텍처라는 용어의 개념은 굉장히 광범위 하다.
	1. IT 에서는 '시스템 아키텍처', '소프트웨어 아키텍처', '데이터 아키텍처', '네트워크 아키텍처' 등 분야를 명시하여 부르는것이 보통.
3. 프론트엔드에서 말하는 아키텍처란?
	1. **"프론트엔드 코드를 어떻게 구조화하고, 데이터를 어떻게 흐르게 할 것인가"** 에 대한 설계
4. 주요 구성 요소
	1. **컴포넌트 구조**
		1. 화면을 어떻게 나누고 조합할지의 설계

			```javascript
			❌ 나쁜 예: 하나의 파일에 모든 것
			<App> ← 여기에 헤더, 로그인, 상품목록, 장바구니 다 들어있음 (3000줄)
			
			✅ 좋은 예: 역할별로 분리
			<App>
			  ├── <Header>
			  ├── <ProductList>
			  │     └── <ProductCard>
			  └── <Cart>
			```

		2. 재사용 가능한 작은 단위의 컴포넌트로 UI 구성
		3. 대표 패턴 예시) Atomic Design
			- Atom(원자): Button, Input 같은 최소 단위
			- Molecule(분자): Atom을 조합한 SearchBar
			- Organism(유기체): Molecule을 조합한 Header
			- Page: 전체 화면
	2. **상태 관리**
		1. 데이터를 어디에 두고 어떻게 흐르게 할 것인가
		2. 전역 / 지역 상태를 적절히 분리하여 데이터 흐름 제어
			1. 로컬
				1. 그 컴포넌트만 사용
				2. 예) 버튼 hover 여부, input 입력값, 아코디언 열림/닫힘, 폼 유효성 검사 결과
			2. 전역
				1. 여러 곳에서 공유
				2. 예) 로그인 유저 정보, 다크모드 설정, 장바구니, 언어 설정
			3. 서버
				1. 서버에서 받아오는 데이터
				2. 예) 상품 목록, 댓글 목록, 유저 프로필
	3. **폴더 구조**
		1. 파일을 어떻게 나눌 것인가
		2. 기능(Feature) 기반 또는 계층(Layer) 기반으로 파일을 조직화
			1. 기능별 분리 (요즘 많이 한다고 함)

				```javascript
				src/
				  features/
				    auth/          ← 로그인 관련 모든 것
				      components/
				      hooks/
				      api/
				    product/       ← 상품 관련 모든 것
				      components/
				      hooks/
				      api/
				```

			2. 유형별 분리 (작은 프로젝트에 적합하다고 함)

				```javascript
				src/
				  components/   ← 모든 컴포넌트
				  hooks/        ← 모든 훅
				  utils/        ← 모든 유틸
				  api/          ← 모든 API 호출
				```

5. 아키텍쳐 스타일 및 패턴
	1. **모놀리식(Monolithic)**
		1. `하나의 큰 앱 안에 로그인 + 결제 + 채팅 + 검색이 다 들어있음`
		2. 단일 코드베이스로 관리되는 일반적인 방식. 소규모에 적합
		3. 모든 기능이 하나의 덩어리
		4. 장점
			1. 개발/배포가 단순
		5. 단점
			1. 하나가 터지면 전체가 터짐, 규모가 커질수록 느려짐
	2. **마이크로 프론트엔드(Micro Frontend)**
		1. `로그인 서비스 / 결제 서비스 / 채팅 서비스가 각각 따로 존재`
		2. 대규모 서비스에서 프론트엔드를 기능별로 분리하여 독립적으로 개발 및 배포
		3. 기능별로 쪼갠 독립적인 서비스들
		4. 장점
			1. 하나가 터져도 나머지는 멀쩡, 독립 배포 가능
		5. 단점
			1. 관리가 복잡해짐
	3. **MVC (Model - View - Controller)**
		1. 관심사를 데이터/화면/제어로 분리해서 유지보수를 쉽게 만드는 패턴
		2. 가장 오래되고 기본이 되는 패턴
		3. Model
			1. 데이터 담당
			2. 예) 유저 정보, 상품 목록
		4. View
			1. 화면 담당
			2. 예) 사용자가 보는 UI
		5. Controller
			1. 둘 사이를 연결
			2. 예) 버튼 클릭 → 데이터 변경
	4. **MVP / MVVM**
		1. 로직(Container)과 화면(Presentational)을 분리하여 재사용성 향상 (최근엔 커스텀 훅으로 대체되는 추세)
		2. **MVP**
			1. Controller 대신 **Presenter**가 View와 Model을 중재. View는 완전히 수동적
		3. **MVVM**
			1. Controller 대신 **ViewModel**이 데이터를 가공해서 View에 자동으로 반영 → React, Vue가 이 방식
	5. **클린 아키텍처(Clean Architecture)**
		1. UI, 데이터베이스 등과 비즈니스 로직을 완벽히 분리하여 어떤 것이 바뀌어도 핵심 로직은 영향받지 않게 만드는 설계 원칙. 유지보수성 극대화
		2. 레이어 구조

			```javascript
							┌─────────────────────────┐
			        │   Frameworks & Drivers  │  ← 가장 바깥 (React, Next.js, Axios)
			        │  ┌───────────────────┐  │
			        │  │    Interface      │  │  ← UI 컴포넌트, API 어댑터
			        │  │  ┌─────────────┐  │  │
			        │  │  │  Use Cases  │  │  │  ← 앱의 동작 규칙
			        │  │  │  ┌───────┐  │  │  │
			        │  │  │  │Entity │  │  │  │  ← 핵심 비즈니스 규칙 (가장 안쪽)
			        │  │  │  └───────┘  │  │  │
			        │  │  └─────────────┘  │  │
			        │  └───────────────────┘  │
			        └─────────────────────────┘
			```

			1. **Entity (가장 안쪽)**
				- 앱의 핵심 비즈니스 규칙
				- 어떤 기술도 의존하지 않는 순수한 로직
				- 예) "주문 금액이 0원 이하면 안 된다", "유저는 이메일 형식이어야 한다"
			2. **Use Case**
				- 앱이 실제로 하는 동작들
				- Entity를 조합해서 기능을 만드는 곳
				- 예) "유저가 로그인한다", "상품을 장바구니에 담는다"
			3. **Interface (어댑터)**
				- 바깥 세상과 안쪽 레이어를 연결하는 번역기
				- 예) API 응답 데이터를 Entity 형태로 변환, UI 이벤트를 Use Case로 전달
			4. **Frameworks & Drivers (가장 바깥)**
				- 실제 사용하는 기술들
				- 예) React, Next.js, Axios, LocalStorage
	6. **CSR / SSR / SSG 렌더링 방식**
		1. CSR
			1. 브라우저에서 렌더링
			2. JS가 화면을 그림. 초기 로딩 느림, SEO 불리
		2. SSR
			1. 서버에서 렌더링
			2. 서버가 HTML 완성해서 전달. SEO 좋음
		3. SSG
			1. 빌드할 때 렌더링
			2. 미리 HTML 생성. 가장 빠름
