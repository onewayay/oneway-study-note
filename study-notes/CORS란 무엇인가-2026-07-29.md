> CORS는 브라우저의 동일 출처 정책(SOP) 때문에 기본적으로 차단되는 다른 출처 간 리소스 요청을, 서버가 응답 헤더(Access-Control-Allow-Origin 등)로 허용해 주는 보안 메커니즘입니다. 단순 요청은 바로 전송 후 응답 헤더를 확인하고, 복잡한 요청은 먼저 OPTIONS 메서드로 프리플라이트 요청을 보내 서버의 허용 여부를 확인합니다. 즉, CORS는 동일 출처 정책을 꺠뜨리는 것이 아니라 서버의 동의하에 안전하게 예외를 두는 프로토콜입니다.


###  동일 출처 정책 SOP (Same-Origin Policy)


	CORS를 알기 위해  알아야할 내용임

	1. 동일 출처 정책이란?
		1. <u>같은 출처에서 온 리소스만 자유롭게 공유할 수 있다는 규칙</u>
		2. 아래 3가지가 모두 같아야 동일 출처로 인정된다.
			1. **프로토콜**
				1. ex) http://, https://
			2. **호스트**
				1. ex) example.com, sub.example.com
			3. **포트**
				1. ex) :80, :443, :3000
	2. 예시로 보는 동일 출처 정책
		1. [https://a.com](https://a.com/) 이라는 웹사이트가 있다고 가정

		| 요청하는 URL           | 출처 비교                                  | 결과                | 이유                  |
		| ------------------ | -------------------------------------- | ----------------- | ------------------- |
		| https://a.com/page | https + [a.com](http://a.com/) + : 443 | 성공 (Same-Origin)  | 프로토콜, 호스트, 포트 모두 동일 |
		| http://a.com       | http가 다름                               | 실패 (Cross-Origin) | 프로토콜 불일치            |
		| https://b.com      | b.com이 다름                              | 실패 (Cross-Origin) | 호스트 불일치             |
		| https://a.com:8080 | :8080이 다름                              | 실패 (Cross-Origin) | 포트 불일치              |

		1. 443포트란?
			1. HTTPS 통신의 기본포트 URL 뒤에 포트가 없으면 기본적으로 443포트로 이동한다.
	3. 왜 이런 정책이 필요할까?
		1. 예시
			1. [my-bank.com](http://my-bank.com/) 에 로그인한 상태에서 악의적인 사이트 [evil.com](http://evil.com/) 에 접속했을 때 evil.com 의 스크립트가 마음대로 my-bank.com 에 요청을 보내 계좌 정보를 탈취
		2. 위 예시와 같은 상황을 막기 위해 <u>다른 출처의 리소스에 무분별하게 접근하는 것을 막는 웹 보안 장치가 동일 출처 정책</u>이다.
	4. 하지만 다른 출처의 리소스를 가져와 사용하는 것은 필요하고, 흔한 일이다.
		1. 예시
			1. [my-blog.com](http://my-blog.com/) 이라는 블로그 사이트에서 [api.weather.com](http://api.weather.com/) 이라는 날씨 정보 API를 호출하여 오늘 날씨를 보여주고 싶다면?
		2. 위의 예시는 동일 출처 정책 때문에 API로 보낸 요청이 차단되어 CORS 에러가 나온다.
		3. 그렇다면 해결책은? → CORS

### 교차 출처 리소스 공유 CORS (Cross-Origin Resource Sharing)

	1. CORS란?
		1. <u>서로 다른 출처 간에 리소스를 주고받도록 허용하는 공식적인 메커니즘</u>
		2. **허용 여부는 요청을 보내는 쪽이 아닌 리소스를 제공하는 서버 쪽에서 결정한다.**
			1. 요청을 받은 서버가 응답 헤더에 이곳에서 오는 요청을 허락하며, <u>리소스를 줘도 괜찮다는 특별한 표시(Access-Control-Allow-Origin)를 담아 브라우저에게 보내면 브라우저는 이를 확인하고 데이터를 정상적으로 처리</u>한다.
	2. CORS의 작동 방식
		1. 단순 요청
			1. 특정 조건을 만족하는 <u>간단한 요청</u>
			2. 아래 조건을 모두 만족해야 함
				1. **요청 메서드**
					1. GET, HEAD, POST 중 하나만 사용해야 한다.
				2. **헤더**
					1. 기본 헤더 외에 Accept, Accept-Language, Content-Language, Content-Type 등 몇가지 헤더만 허용한다.
				3. **Content-Type 헤더**
					1. application/x-www-form-urlencoded, multipart/form-data, text/plain 중 하나여야 한다.
			3. 브라우저가 서버로 요청을 보낸 다음 서버의 응답 헤더에 Access-Control-Allow-Origin이 있는지 확인하여 CORS 위반 여부를 판단한다.
			4. 작동 흐름
				1. 브라우저가 서버에 요청을 보낸다.
				2. 서버가 응답을 보내며 Access-Control-Allow-Origin 헤더로 **허용 Origin을 명시**한다.
				3. 브라우저가 응답 헤더를 검사한 뒤, **허용된 경우에만 웹 사이트에 데이터를 전달**한다.
		2. 프리플라이트 요청
			1. 단순 요청의 조건을 벗어나는 <u>더 복잡한 요청을 보내기 전에 서버에 먼저 허락을 구하는 절차</u>
				1. 이때 브라우저는 OPTIONS 라는 메서드를 사용한다.
			2. 작동 흐름
				1. 브라우저가 서버로 OPTIONS 요청을 보낸다.
				’안녕, 나 https://my-blog.com이야. PUT 메서드랑 Content-Type: application/json 헤더로 본 요청을 보내려고 하는데 괜찮을까?’ 라는 정보가 담겨 있다.
				2. 서버가 해당 출처, 메서드, 헤더가 허용 목록에 있는지 확인 후 Access-Control-Allow-Origin, Access-Control-Allow-Methods, Access-Control-Allow-Headrs 등의 헤더를 포함한 응답을 브라우저로 보낸다.
				3. 서버로부터 허가를 받은 브라우저는 실제 요청을 서버로 전송한다.
				4. 서버가 본 요청을 처리한 후 브라우저로 실제 요청에 대한 데이터를 응답한다.
			3. 프리플라이트 과정 덕분에 서버는 자신이 처리할 수 없는 위험하거나 낯선 요청을 사전에 차단할 수 있다.
