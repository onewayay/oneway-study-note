# Git, GitHub 이게 뭐고 왜 쓰는가?


> Git

1. Git 이란?
	1. 코드의 변경 이력을 관리하는 **버전 관리 도구**
	2. git이 없는 쌩 버전관리
		1. 최종.js, 최최종.js, 진짜최종.js, 진짜진짜최종.js …
	3. git으로 버전관리
		1. 코드 변경할 때마다 버전으로 관리 가능 (스냅샷 찍듯이)
		2. 언제든 원하는 시점으로 돌아갈 수 있음
		3. 누가 언제 뭘 바꿨는지 다 기록됨
2. 관련 핵심 내용
	1. Repository (저장소)
		1. Git으로 관리되는 프로젝트
		2. 로컬 저장소 (local)
			1. 내 컴퓨터에 있는 것
			2. git init을 통해 관리하는 폴더 (폴더에 .git 폴더 있음)
		3. 원격 저장소 (remote)
			1. 서버(GitHub)에 있는 것
	2. Commit (커밋)
		1. 변경사항을 저장하는 스냅샷 (세이브 포인트)
		2. 커밋할 때는 메시지를 남길수 있다.
			1. 어떤 기능을 수정했는지 등등
			2. 랜덤한 해시를 통해 관리된다.
	3. Branch (브랜치)
		1. 메인 코드에서 독립된 작업 공간
		2. 브랜치를 쓰는 이유
			1. 여러명이 각자 공간에서 독립적인 작업 가능
			2. 안정성 확보
				1. main 브랜치
					1. 실제 서비스되는 안정적인 코드
				2. 기능 브랜치
					1. 새 기능 개발할 때 여기서 작업
					2. 완성되면 main에 합침 (merge)
					3. main은 항상 안전하게 유지
	4. Merge (머지)
		1. 브랜치를 합치는 것
		2. 각 브랜치에서 작업한 내용들을 하나로 합칠 때 사용
3. Git 동작 과정
	1. 간단 요약
		1. Working Directory → Staging Area → Repository
		2. 코드 수정 → git add → git commit
	2. Working Directory
		1. 로컬(내 컴퓨터)에서 현재 작업 중인 파일
	3. Staging Area
		1. 커밋할 파일을 선택하는 공간
		2. add 상태
	4. Repository
		1. 실제로 커밋이 저장되는 공간
		2. commit 상태
4. 자주 쓰는 Git 명령어

	```bash
	# 저장소 초기화
	git init
	
	# 현재 상태 확인
	git status
	
	# 파일 staging
	git add .           # 전체
	git add index.js    # 특정 파일
	
	# 커밋
	git commit -m "메시지"
	
	# 브랜치 생성
	git branch feature/login
	
	# 브랜치 이동
	git checkout feature/login
	git switch feature/login    # 최신 방식
	
	# 브랜치 생성 + 이동 한번에
	git checkout -b feature/login
	
	# 머지
	git merge feature/login
	
	# 로그 확인
	git log
	```


> GItHub

1. GitHub 이란?
	1. Git 저장소를 인터넷에 올려서 관리하고 협업하는 플랫폼
2. Git이랑 GitHub 차이
	1. Git
		1. 도구 (버전 관리 프로그램)
		2. Git은 GitHub 없이도 사용 가능
	2. GitHub
		1. 플랫폼 (Git 저장소를 올리는 웹사이트)
		2. GitHub는 Git 기반으로 동작
3. GitHub의 주요 기능
	1. Remote Repository (원격 저장소)
		1. 내 컴퓨터(로컬)의 코드를 GitHub 서버에 올린 공간
		2. 백업 역할
		3. 팀원들과 공유 가능
		4. 로컬 → GitHub 올리기
			1. `git push origin main`
		5. GitHub → 로컬 받아오기
			1. `git pull origin main`
	2. Pull Request (PR)
		1. 내 브랜치를 main에 합쳐도 될지 요청하는 것
		2. 흐름
			1. feature/login 브랜치에서 작업
			2. GitHub에 push
			3. PR 생성 ("로그인 기능 완성했어요, 리뷰해주세요")
			4. 팀원들이 코드 리뷰
			5. 승인되면 main에 merge
	3. Issue
		1. 버그, 기능 요청, 할 일을 등록하는 티켓 시스템
		2. PR이랑 연결할 수 있다
			1. PR merge되면 해당 이슈는 이슈 자동으로 닫힘
	4. Fork
		1. 다른 사람의 저장소를 내 계정으로 복사하는 것
		2. 오픈소스 기여할 때 씀
		(오픈소스 프로젝트 Fork → 내 저장소에서 수정 → 원본 저장소에 PR 보냄 → 승인되면 내 코드가 오픈소스에 반영)
	5. GitHub Actions
		1. Push, PR 등 이벤트 발생 시 → 자동으로 테스트, 빌드, 배포 실행하도록 설정 가능

> 왜 쓰는가??


### Git

1. 되돌릴 수 있다.
	1. 코딩하다보면 아래같은 상황이 발생한다.
		1. 잘 되던 기능이 다른 기능을 개발하고나니 갑자기 동작하지 않는다.
		2. 완전히 잘못 개발해서 며칠전으로 되돌리고 싶다.
		3. AI가 무언가 수정했는데 갑자기 전체가 이상해졌다.
		4. … 등등
	2. 이런 상황에서 커밋의 체크포인트로 되돌릴 수 있다.
2. 안전하게 개발이 가능하다.
	1. 브랜치를 통해 안전한 원본(main)에 영향을 주지 않고 마음껏 개발 가능
3. "내가 뭘 바꿨는지" 항상 알 수 있다.
	1. 커밋 메세지를 통해 알 수 있다.
	2. 커밋 내역의 코드 수정부분을 확인해서 알 수 있다.
4. 여러 기능을 동시에 개발할 수 있다.
	1. 브랜치 통해 각 기능을 독립적으로 개발 가능

### GitHub

1. 내 코드가 사라지지 않는다.
	1. 내 컴퓨터(local)에서 프로젝트가 통채로 날라가더라도 GitHub을 통해 다시 받아올 수 있다.
2. 팀원들과 같은 코드로 작업할 수 있다.
	1. 모두 같은 GitHub 저장소를 바라봄
	2. 각자 브랜치에서 작업 후 PR로 코드 리뷰 후 merge
	→ 항상 최신 코드가 어디있는지 명확
3. 코드 리뷰가 가능하다.
	1. PR 기능을 통해 머지 전에 문제를 미리 확인하고 바로 잡을 수 있다.
	2. 서로 코드를 보면서 같이 성장할 수 있다.
4. 이슈로 할 일을 체계적으로 관리할 수 있다.
	1. 나에게 주어진 일을 체계적으로 관리 가능 + 누가 어떤일을 맡았는지 확인 가능
